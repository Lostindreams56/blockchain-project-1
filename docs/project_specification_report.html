1. System Architecture & High-Level Design

The Ethereum Fraud Detection Platform is architected as a decoupled, multi-tier distributed system. Rather than tightly coupling blockchain indexing with frontend rendering, the platform divides responsibilities across five distinct tiers:

  1. Presentation Tier (FraudOS 95 Frontend): A React 18, TypeScript, and Vite single-page application (SPA) styled with custom 1995 2-stage outset/inset bevel borders, MS Sans Serif system typography, window manager state, and Web Audio API synthesized sounds.
  2. API Gateway & Orchestration Tier (Express Server): A Node.js LTS server providing JWT authentication, token rotation, rate limiting, request validation via Zod schemas, structured logging via Pino, and API routing.
  3. Machine Learning Microservice (FastAPI Inference Daemon): A Python 3.13 microservice exposing low-latency REST endpoints for XGBoost inference and TreeSHAP explainability.
  4. Data & Persistence Tier (MongoDB Atlas Cluster): Cloud document store with strict collection boundaries (users, sessions, ethereum_dataset, investigations).
  5. Decentralized Blockchain Ingestion Tier: Hybrid ingestion model leveraging both Ethereum JSON-RPC nodes and indexed block explorer APIs (Etherscan/Alchemy).
Architectural Insight: The Blockchain Reverse-Index Ingestion Problem
Standard Ethereum JSON-RPC nodes (Geth, Nethermind) organize state in block-level Patricia Merkle tries. They natively support eth_getBalance and eth_getBlockByNumber, but do not maintain an account-to-transaction reverse index. Querying lifetime transactions using only standard RPC requires scanning >21 million blocks. Hence, our architecture utilizes a hybrid ingestion model: indexed APIs for historical lifetime metrics combined with direct JSON-RPC for real-time balance and contract bytecode verification.

4. Entity-Relationship (ER) Diagram & Database Design

The database architecture is deployed on a dedicated MongoDB Atlas cloud cluster using Mongoose ODM. To prevent accidental data contamination, our design enforces:

  • Strict Database Scoping: All Mongoose models explicitly bind to dbName: ethereum_fraud_dev. The application is strictly isolated from any external sample collections (such as Atlas's default sample_mflix).
  • Independent Collection Lifecycles: Historical labeled dataset records, user authentication credentials, and actual forensic investigation dossiers are segregated into four separate collections.
  • Zero Startup Auto-Seeding: Normal server initialization performs zero write operations. All data ingestion requires explicit operator execution.

6. User Interface (UI) Design — FraudOS 95 Retro Workstation

Rather than adopting the ubiquitous, generic "AI SaaS" aesthetic (purple gradients, bloated whitespace, translucent glowing cards), the platform implements an intentional, nostalgic, and compact Windows 95 Retro Desktop Workstation (FraudOS 95).

6.1 Design Principles & Technical Implementation

  • 2-Stage Outset / Inset Bevel Borders: Every window, button, and input element uses authentic 1990s border highlights (#FFFFFF top/left, #808080 and #000000 bottom/right) to simulate hardware-rendered GUI depth.
  • MS Sans Serif Typography: Crisp 8pt to 11pt system typography with tight line spacing, maximizing on-screen data density for compliance analysts.
  • Web Audio API Sound Synthesis: Zero audio assets. Pure mathematical audio synthesis (440Hz clicks, 220Hz/180Hz double error bonks, and ascending chord chimes) with optional toggle defaulting to OFF for accessibility.
  • Dynamic Window Management: Native window manager supporting focus stacking, draggable title bars, taskbar tabs, minimize, maximize, and desktop shortcut icons.

7. Machine Learning Engineering & Model Evaluation

The machine learning service is engineered to resolve extreme class imbalance (22.14% fraud prevalence) and eliminate data leakage while delivering sub-second inference.

7.1 Data Leakage Prevention & Stratification

  • Entity-Aware Splitting: The raw Ethereum dataset contains individual addresses with multiple transactions. Splitting randomly on rows causes duplicate addresses in train and test sets, artificially inflating accuracy (address memorization). Our pipeline splits strictly on unique entity accounts (70% Train, 15% Validation, 15% Test).
  • Strict Isolation of Fit: Preprocessing transformers (SimpleImputer, VarianceThreshold, RobustScaler) fit exclusively on the training partition and transform validation/test partitions without peeking.
